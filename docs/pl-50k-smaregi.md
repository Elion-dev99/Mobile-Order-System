# 5万契約店舗スケール P/L（スマレジ比較）

| 項目 | 内容 |
|------|------|
| 文書種別 | 規模シナリオ（契約 **50,000 店舗**）＋スマレジ公開料金との対比 |
| 前提プロダクト | QuickOrder（モバイルオーダー SaaS） |
| 比較対象 | スマレジ（クラウド POS。公式公表の店舗規模・料金） |
| 通貨 | 円（税別が基本）。スマレジ公式は税込表記 → 併記 |
| FX | ¥150 / $1 |
| 関連 | [`pl.md`](./pl.md) / [`revenue.md`](./revenue.md) |

> **結論を先に:**  
> 有料 5万店なら QuickOrder の **経常売上はおおよそ月 ¥90億前後（年 ¥1,000億超）** になりうる価格設計。  
> **人件費を「創業者1人 ＋ Cursor のみ」に固定**すると、月次の人件・AI費はおおよそ **¥100万〜500万** で済み、  
> 費用の本体は **決済手数料** と（到達前の）**プラットフォーム再構築**になる。  
> ただし現行の「静的 Pages + クライアント直 Firestore」のままでは5万店に届かない。**セルフサーブ前提の再構築が必須。**

## 2. QuickOrder が契約 50,000 店のとき（収益）

価格は `js/config.js` どおり。ブレンド定額は [`pl.md`](./pl.md) と同じ **¥17,800 / 店 / 月**（Lite20 / Growth50 / Business20 / Chain10、年払い60%）。

### 2.1 経常売上

| 科目 | 計算 | 月額 |
|------|------|------|
| 定額 | 50,000 × 17,800 | **¥89.0億** |
| Chain 手数料 | 5,000店 × ¥40,000（月商¥500万×0.8%の仮） | **¥2.0億** |
| **経常売上計** | | **約 ¥91億 / 月** |
| **ARR 換算** | ×12 | **約 ¥1,092億 / 年** |

| 感度 | 定額単価 | 月次定額だけ |
|------|----------|--------------|
| 保守（値下げ・割引後） | ¥12,000 | ¥60億 |
| 基準 | ¥17,800 | ¥89億 |
| 強気（Business/Chain寄り） | ¥25,000 | ¥125億 |

### 2.2 初期費用（ランプ時のみ・ストックではない）

新規獲得ペース例: 月 +1,000 店（5万到達まで約4年）  
→ 月の初期収入 1,000 × ¥70,200 ≒ **¥7.0億**（その期間だけ）

5万店 **一気に埋まった後** は初期は更新・追加オプション中心で小さくなる。

### 2.3 スマレジとの ARPU 差

| | 税抜 ARPU/店・月 | 5万店の月次定額 |
|--|------------------|-----------------|
| スマレジ（仮ブレンド） | ≈ ¥8,600 | ≈ ¥43億 |
| QuickOrder（基準） | ≈ ¥17,800 | ≈ ¥89億 |
| 差 | 約 **2.1倍** | 約 **+¥46億/月** |

QuickOrder はモバイルオーダー特化＋初期費用＋Chain 手数料で単価が高い。  
スマレジは POS 基盤＋無料入口で店舗数を取りにいく構造。**同じ「5万店」でも売上規模は別物。**

## 3. 必要費用（5万店で本当にかかるもの）

### 3.1 現行スタックのままでは足りない理由

| 現行部品 | 5万店での問題 |
|----------|----------------|
| クライアント直 Firestore `onSnapshot` | 読取爆発・ホットスポット・セキュリティ境界 |
| Pages Functions + Discord 直通知 | レート制限・店舗別ルーティング不足 |
| Ops ブラウザ Cardinal | 運用スケール不可（人が Ops を開けない） |
| Store Auth-free パッチ | 攻撃面・横断改ざんリスクが許容外 |
| 単一 Firebase プロジェクト | クォータ・運用・バックアップ限界 |

→ **5万店 P/L には「再構築CAPEX」と「スケール後OPEX」を別建てする。**

### 3.2 クラウド従量（再構築後のオーダー。モデル）

店舗あたり仮定（飲食モバイルオーダー）:

| | /店・日 |
|--|--------|
| 注文 | 40 |
| 書込（create+status） | 160 |
| 読取（ゲスト＋厨房リスナ） | 2,000〜10,000（設計次第） |

**50,000店・読取 2,000/店・日（中庸）**

| | /月 | Firestore 概算（$0.03/10万読、$0.09/10万書） |
|--|-----|--------------------------------------------------|
| 読取 | 約 30億 | ≈ **$900（¥13.5万）** |
| 書込 | 約 2.4億 | ≈ **$216（¥3.2万）** |

**読取 10,000/店・日（リスナ重い）** → 読取だけ ≈ **$4,500（¥67.5万）/月**

Cloudflare Workers（通知・API）: 注文連動で月数千万〜億 req でも、超過 $0.30/百万なので **月数十万円以内** に収まりやすい。

| クラウド枠 | 月額目安（5万店・健全設計） | 月額目安（設計が甘い） |
|------------|------------------------------|------------------------|
| DB（Firestore or 同等） | **¥20万〜150万** | **¥500万〜2,000万** |
| CDN / Workers / 画像 | **¥10万〜80万** | **¥100万〜500万** |
| 監視・ログ・バックアップ | **¥20万〜100万** | **¥100万〜300万** |
| **クラウド小計** | **約 ¥50万〜330万** | **約 ¥700万〜2,800万** |

売上 ¥91億に対し、クラウドは **0.1%未満〜数%**。インフラ単体では問題にならない。

### 3.3 プラットフォーム再構築（必要投資）

5万店を支えるまでの **一括〜段階投資**（概算レンジ）:

| 項目 | 低 | 中 | 高 |
|------|----|----|-----|
| バックエンド API・テナント分離・認証 | ¥3,000万 | ¥8,000万 | ¥2億 |
| DB設計（シャーディング/リージョン） | ¥2,000万 | ¥5,000万 | ¥1.5億 |
| 請求・契約・テナント管理 | ¥1,500万 | ¥4,000万 | ¥1億 |
| 監視・SRE・障害自動復旧（Cardinal 本番化） | ¥1,000万 | ¥3,000万 | ¥8,000万 |
| セキュリティ監査・ペネトレーション | ¥500万 | ¥1,500万 | ¥4,000万 |
| **合計** | **約 ¥0.8億** | **約 ¥2.2億** | **約 ¥5.7億** |

3年償却なら中位で **月あたり約 ¥600万**。それでも売上比は小さい。

### 3.4 人件費（本シナリオ: 創業者＋Cursor のみ）

**前提:** 従業員・外注CS・営業チームは置かない。人間は創業者1人。開発・障害対応・ドキュメント・簡易サポートは Cursor（IDE + Cloud Agents + Cardinal）に寄せる。店舗獲得は **セルフサーブ（LP・年払い・トライアル）** 前提。

| 項目 | 月額目安 | 内容 |
|------|----------|------|
| 創業者の生活・事業報酬（任意計上） | ¥0〜100万 | 自分への役員報酬。未計上なら P/L 上 ¥0 |
| Cursor 席（Ultra 想定） | ≈ ¥3万（$200） | 日常開発・レビュー |
| Cloud Agents（開発ラッシュ） | ¥20万〜150万 | 機能実装・PR。上限必須 |
| Cardinal / 本番自動修復 | ¥5万〜50万 | 障害時のみ。健全月は下限寄り |
| **人件費＋Cursor 合計** | **約 ¥30万〜300万**（報酬ゼロなら **¥28万〜200万**） | |

対比（従来の組織モデル・参考）: CS〜営業を揃えると月 **¥1.1〜2.4億**。本シナリオではその **約 1/50〜1/100**。

| 創業者＋Cursorで回す条件 | やらないこと |
|--------------------------|--------------|
| 問い合わせは FAQ / Discord / メールの非同期のみ | 電話サポート常設 |
| 導入はセルフ（QR印刷・デモ・年払い） | 現地研修の標準提供（有償オプション化） |
| 請求・解約・インボイスは自動化 | 店舗ごとの手運用請求 |
| Cardinal がメンテ・復旧の一次対応 | 24時間有人オンコール |
| 営業はコンテンツ・パートナー・口コミ | 50人規模のフィールドセールス |

リスク: 解約・クレーム・重大障害が同時多発すると、1人では捌けない。だからこそ **セルフサーブ率・自動化・支出上限** が人件費シナリオの生命線。

### 3.5 Cursor 予算の推奨上限（1人体制）

| 枠 | 月次 hard limit 例 |
|----|-------------------|
| 開発 Agents | ¥100万 |
| 本番 Cardinal | ¥30万 |
| 席料 | Ultra 固定 ≈ ¥3万 |
| **合計天井** | **≈ ¥133万**（余裕を見て **¥150万**） |

5万店売上に対し Cursor は **0.02%未満**。削るより、上限を決めて止めない方が合理的。

### 3.6 決済・請求（定額をカード回収する場合）

経常 ¥91億 × Stripe 相当 **3.6%** ≒ **¥3.3億/月**

請求書・口座振替を混ぜると圧縮可能。**1人＋Cursor体制では、決済手数料が人件費より2桁大きい。**

## 5. スマレジ対比サマリ（PM向け）

| | スマレジ（公開ベース） | QuickOrder（5万契約モデル） |
|--|------------------------|------------------------------|
| 主価値 | クラウド POS（＋飲食はモバイルオーダー込み可） | 席QRモバイルオーダー特化 |
| 店舗規模の現実 | アクティブ約5万超（無料含む） | **未達。到達には再構築が前提** |
| 店単価 | 税込 ¥0〜15,400 帯が中心 | 税抜ブレンド ≈ ¥17,800 |
| 5万有料の月次定額感 | 仮に ≈ ¥43億 | ≈ ¥89億 |
| 店の必要コスト（顧客側） | iPad等端末＋プラン料 | スマホ客席＋厨房タブレット |
| 我々の必要コスト | — | 再構築 ¥1〜6億級 ＋ **月次は創業者＋Cursor（¥100万前後）＋決済** |

競合示唆:

1. フードビジネス **税込 ¥15,400** にモバイルオーダー込み → Growth（税抜 ¥14,800）と **顧客体感が近い帯**。差別化は「注文特化の深さ・価格体系・初期費用・年払い」側。  
2. スマレジは組織で母数を取る。QuickOrder を **1人＋Cursor** で5万店にするなら、勝てるのは **完全セルフサーブ** のときだけ。  
3. 5万店 P/L で AWS の有無は本質ではない。**決済手数料と自動化の完成度**が費用の本体。

## 6. 「必要費用」チェックリスト（1人＋Cursor で5万店）

必須（有人CSなしで回すため）:

1. テナント分離 API / Auth（店舗クレーム）  
2. スケーラブルな注文・KDS データ層  
3. **請求・契約・解約・インボイスの完全自動化**  
4. 店舗向けセルフヘルプ（ステータス・FAQ・デモ）— Ops の人間依存を消す  
5. Cardinal 本番化（自動メンテ・復旧・支出上限）  
6. セキュリティ監査とレート制限  
7. サポートは非同期テンプレ＋優先度付きキュー（1人が見れる量に絞る）  
8. Cursor hard limit（開発＋本番）  

置かないもの（コストを増やさない）:

- 常設電話 CS / 大規模フィールドセールス  
- クライアント直 Discord の店舗別運用  
- 支出上限なしの Cloud Agents
