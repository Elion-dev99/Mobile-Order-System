## 3. 費用モデル（実際に使うサービス）

### 3.1 コスト構造図

```text
売上（定額 + 初期 + Chain手数料 + オプション）
  − 変動費寄り
      · Firebase / Firestore（読取・書込・保存・egress）
      · Cloudflare Workers Paid（Functions 超過時）
      · Cursor Cloud Agents（障害時 dispatch / 開発）
      · 決済手数料（Stripe 接続後。現状スタブ＝¥0）
  − 固定費寄り
      · Cursor 席料（Pro / Teams）
      · Cloudflare ベース（$0 or $5）
      · ドメイン・メール・会計ツール
      · 人件費（開発・サポート・導入）← 最大の「見えない」費用
  ＝ 営業利益（簡易）
```

### 3.2 Cloudflare Pages / Workers

| 項目 | 目安 |
|------|------|
| 静的配信 | **無料・帯域無制限** |
| Functions Free | 10万 req/日（notify / cardinal / maintenance） |
| Workers Paid | **$5/月（≒¥750）** ＋ 1,000万 req 込み、超過 $0.30/百万 |

Cardinal cron は毎時1回程度。通常は Free で足りる。本番で通知・tick が増えたら Paid $5 を推奨。

### 3.3 Firebase / Firestore（GCP）

| 項目 | 無料枠 | 超過目安 |
|------|--------|----------|
| 読取 | 5万/日 | **$0.03 / 10万件** |
| 書込 | 2万/日 | **$0.09 / 10万件** |
| 保存 | 1 GiB | 約 $0.18/GiB・月 前後 |
| egress | 10 GiB/月 | リージョン依存 |

Auth（Email/Password）は標準プロバイダ利用なら席料なし。  
**ホストは Cloudflare なので Firebase Hosting 費用は原則発生しない。**

注文中心の SaaS では、厨房の `onSnapshot` が読取を稼ぐ。それでも 50店規模でも月額数百〜数千円オーダーになりやすい（設計が荒いと桁が上がるので §5 の監視を推奨）。

### 3.4 Cursor（最大の変動コスト）

| 項目 | 目安 |
|------|------|
| Pro 席 | **$20/月（≒¥3,000）**/人 |
| Pro+ / Ultra | $60 / $200（重い開発時） |
| Teams | $40/人・月 |
| Cloud Agents | **モデル API 従量**（プラン込みクレジット消化後はオンデマンド） |

Cardinal の挙動:

- cron `tick` は **正常時エージェント起動なし**（安い）  
- 障害時のみ Executor / Guardian 起動 → **1回あたり数百円〜数千円以上**もあり得る（モデル・ターン数次第）  
- 開発用 Cloud Agent（機能実装 PR）は別枠で月に数万かかることも多い  

**運用推奨:** Cursor ダッシュボードで **支出上限（hard limit）** を設定。例: 本番 Cardinal ¥10,000/月、開発 ¥30,000/月。

### 3.5 その他

| 項目 | 月額目安 | 備考 |
|------|----------|------|
| Discord | ¥0 | Webhook |
| GitHub Actions | ¥0〜数千 | public / 無料枠内なら実質0。private は分課金 |
| 独自ドメイン | ¥100〜200 | 年額を月割り |
| Google Workspace / メール | ¥0〜2,000 | 任意 |
| Stripe 手数料 | 売上×約 3.6% | **決済接続後**。現状スタブで ¥0 |
| AWS | **¥0** | **未使用** |

### 3.6 人件費（簡易）

インフラ以外で損益を決めるのはここ。

| 役割 | 月あたり想定時間 | 社内コスト仮（¥5,000/時） |
|------|------------------|---------------------------|
| 開発（Cursor 併用） | 40〜80h | ¥20〜40万 |
| 導入・CS | 店数×1〜2h | 10店で ¥5〜10万 |
| 障害当番 | 偶発 | Cardinal が一部代替 |

## 5. 損益分岐の目安

### 5.1 インフラ＋Cursor のみで賄う場合

固定寄りコストを **¥15,000/月**（CF Paid + Cursor Pro + 余裕）とすると:

```text
損益分岐店数 ≒ 15,000 / 17,800 ≒ 1店未満
```

**有料1店（Growth）でインフラは十分ペイする。**

### 5.2 人件費込み（月 ¥300,000 を回す場合）

```text
300,000 / 17,800 ≒ 17店
```

Chain 手数料や初期を足せば **有料 12〜15店** 程度でも届きうる。

### 5.3 Cardinal 費用の感度

| 月間エージェント起動 | 仮単価 | 月額 |
|----------------------|--------|------|
| 健全（0〜2回） | ¥2,000 | ¥0〜4,000 |
| 不安定（10回） | ¥3,000 | ¥30,000 |
| 開発ラッシュ（30回） | ¥4,000 | ¥120,000 |

→ **監視は安いが「直すAI」は高い。** 自動メンテで客席を止め、エージェントは本当に必要なときだけ、が費用最適。

## 6. AWS について（使っていない）

現行は AWS に依存しない。仮に同等を AWS に載せ替えた場合の参考（本番移行案ではない）:

| 役割 | 現行 | AWS 仮 |
|------|------|--------|
| 静的＋エッジ関数 | Cloudflare Pages | CloudFront + Lambda@Edge / Amplify |
| DB | Firestore | DynamoDB / Aurora |
| 月額イメージ（小規模） | ¥0〜数千 | しばしば **¥5,000〜3万〜**（NAT・ALB・ログで膨らみやすい） |

**結論:** 現状の P/L では AWS 行は **¥0**。コスト最適化の主戦場は AWS ではなく **Cursor 従量と人件費**。

## 9. 意思決定メモ（PM向け）

1. **インフラは安い。価格破壊競争に付き合わず、Growth 年払いを主戦場にしてよい。**  
2. **Cursor は「開発加速」と「障害時の保険」。両方無制限にすると利益を食う → 支出上限必須。**  
3. **AWS への移行は現状コスト理由では正当化しにくい**（運用複雑化の方が先）。  
4. **Stripe 接続後は 3〜4% が新しい COGS**。請求書払い併用を検討。  
5. **黒字の鍵は店数×年払い＋初期**。Cardinal の価値は「深夜の人件費代替」として ROI を見る。
